\chapter{Process}\label{process}

\begin{figure}

\centering{

\pandocbounded{\includegraphics[keepaspectratio]{index_files/mediabag/figs/sw_arch.pdf}}

}

\caption{\label{fig-sw-arch}CalCOFI data workflow.}

\end{figure}%

The original raw \textbf{data}, most often in tabular format {[}e.g.,
comma-separated value (*.csv){]}, gets \textbf{ingest}ed into the
\textbf{database} by R
\href{https://github.com/CalCOFI/scripts}{scripts} that use functions
and lookup data tables in the R package
\href{https://calcofi.github.io/calcofi4r/reference/index.html}{\textbf{\texttt{calcofi4r}}}
where functions are organized into \emph{Read}, \emph{Analyze} and
\emph{Visualize} concepts. The application programming interface
(\textbf{API}) provides a program-language-agnostic public interface for
rendering subsets of data and custom visualizations given a set of
documented input parameters for feeding interactive applications
(\textbf{Apps}) using Shiny (or any other web application framework) and
\textbf{reports} using Rmarkdown (or any other report templating
framework). Finally, R scripts will \textbf{publish} metadata (as
\href{https://docs.ropensci.org/EML}{Ecological Metadata Language}) and
data packages (e.g., in Darwin format) for discovery on a variety of
data \emph{\textbf{portals}} oriented around slicing the tabular or
gridded data
(\href{https://coastwatch.pfeg.noaa.gov/erddap/information.html}{ERDDAP}),
biogeographic analysis (\href{https://obis.org}{OBIS}), long-term
archive (\href{https://www.dataone.org}{DataOne},
\href{https://www.ncei.noaa.gov}{NCEI}) or metadata discovery
(\href{https://www.fisheries.noaa.gov/inport/}{InPort}). Every one of
those datasets --- and every one still awaiting ingestion --- also has a
page of its own at
\href{https://calcofi.io/datasets/}{calcofi.io/datasets/}: the
\textbf{dataset catalog}, generated from the same database, joining
every portal it reaches (see \href{portals.qmd}{Portals}). The
\textbf{database} will be spatially enabled by PostGIS for summarizing
any and all data by \emph{\textbf{Areas of Interest}} (AoIs), whether
pre-defined (e.g., sanctuaries, MPAs, counties, etc.) or arbitrary new
areas. (Figure~\ref{fig-sw-arch})

That figure is from 2022. The \textbf{publish} box on it is now real,
and it is generated rather than scripted by hand: at every release one
record per dataset (\texttt{datasets.json}) and one EML document per
dataset are written, and from those two files come the dataset pages,
the DCAT and STAC catalogs, the Darwin Core archives for OBIS, the EDI
packages and ERDDAP's own metadata (Figure~\ref{fig-catalog-flow}). How
a provider's words get into that record --- and what they edit to change
it --- is the subject of \href{metadata.qmd}{Metadata \& the ingest
loop}.

\section{Naming conventions}\label{naming-conventions}

\begin{quote}
There are only two hard things in Computer Science: cache invalidation
and naming things. -- Phil Karlton (Netscape architect)
\end{quote}

Background reading:
\href{https://www.sqlshack.com/learn-sql-naming-conventions/}{Learn SQL:
Naming Conventions} ·
\href{https://drygast.net/blog/post/database_naming_conventions}{Best
Practices for Database Naming Conventions}.

\subsection{Name tables}\label{name-tables}

\begin{itemize}
\tightlist
\item
  Table names are \textbf{singular} and use all lower case.

  \begin{itemize}
  \tightlist
  \item
    Example: \texttt{cruise}, \texttt{site}, \texttt{species},
    \texttt{lookup} (not \texttt{cruises}, \texttt{sites},
    \texttt{lookups})
  \end{itemize}
\end{itemize}

\subsection{Name columns}\label{name-columns}

\begin{itemize}
\item
  To name columns, use
  \href{https://cran.r-project.org/web/packages/snakecase/vignettes/introducing-the-snakecase-package.html}{\textbf{snake-case}}
  (i.e., lower-case with underscores) so as to prevent the need to quote
  SQL statements. (TIP: Use
  \href{https://sfirke.github.io/janitor/reference/clean_names.html}{\texttt{janitor::clean\_names()}}
  to convert a table.)
\item
  Suffix with \textbf{units} where applicable (e.g., \texttt{*\_m} for
  meters, \texttt{*\_km} for kilometers, \texttt{*\_degc} for degrees
  Celsius). See
  \href{https://cran.r-project.org/web/packages/units/vignettes/measurement_units_in_R.html}{units
  vignette}.
\item
  Set the geometry column to \textbf{\texttt{geom}} (used by the
  \href{https://postgis.net}{PostGIS} spatial extension). If a table has
  multiple geometry columns, use \texttt{geom} for the default and
  \texttt{geom\_\{type\}} for the rest (\texttt{geom\_point},
  \texttt{geom\_line}, \texttt{geom\_polygon}).
\end{itemize}

\subsection{Key conventions}\label{key-conventions}

The \textbf{suffix says what kind of value it is}, and this is checked
in review, because a character-valued identifier named \texttt{*\_id} is
a promise the data cannot keep:

\texttt{*\_key} & a \textbf{string} natural key --- meaningful, stable,
human-readable & \texttt{cruise\_key}, \texttt{site\_key},
\texttt{grid\_key}, \texttt{sample\_key}, \texttt{taxon\_key},
\texttt{dataset\_key}, \texttt{ship\_key} \\
\texttt{*\_id} & an \textbf{integer} key --- a source counter or
surrogate & \texttt{cast\_id}, \texttt{bottle\_id},
\texttt{species\_id}, \texttt{obs\_id}, \texttt{hex\_id} \\
\texttt{*\_uuid} & the \textbf{provider's own} identifier for that
record, as they mint it
(\href{https://datatracker.ietf.org/doc/html/rfc4122}{RFC 4122}) &
\texttt{cruise\_uuid}, \texttt{source\_uuid}, \texttt{station\_uuid} \\
\texttt{*\_seq} & an auto-incrementing sequence integer & --- \\
\end{longtable}

\textbf{Natural keys are preferred over surrogates wherever they are
stable}, and the four that carry the integration are worth stating
exactly:

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{cruise\_key} = \texttt{YYYY-MM-NODC}}
  (e.g.~\texttt{1998-02-33JD}) --- and the \texttt{YYYY-MM} is the month
  SWFSC \emph{designates} for the whole cruise, never the month a cast
  or tow happened to fall in. A CalCOFI cruise routinely straddles a
  calendar boundary (5508BD ran 7 Aug -- 25 Sep 1955), and the
  neighbouring month is usually a \textbf{real} cruise of the same ship,
  so keying by event month silently moves casts onto the wrong cruise
  with no foreign key ever failing. Events are keyed by containment in
  the reference cruise's observed date span first, then by the source's
  own designation, then by event month as a last resort --- and which
  rule fired is recorded.
\item
  \textbf{\texttt{sample\_key} =
  \texttt{\{dataset\_key\}:\{sample\_type\}:\{id\}}} (e.g.
  \texttt{calcofi\_bottle:cast:7644}) --- globally unique across
  datasets \emph{and} across event levels, so a site, a tow, a net, a
  cast and a bottle can share one table without collision.
\item
  \textbf{\texttt{site\_key}} is the CalCOFI station in
  \texttt{"line\ station"} form (\texttt{"090.0\ 062.0"});
  \textbf{\texttt{grid\_key}} is the shared grid cell;
  \textbf{\texttt{dataset\_key}} = \texttt{\{provider\}\_\{dataset\}} is
  the provenance stamp on every observation.
\item
  \textbf{\texttt{taxon\_key}} is a lowercase authority prefix plus that
  authority's accepted id ---
  \texttt{worms:\textless{}AphiaID\textgreater{}}, or
  \texttt{itis:\textless{}TSN\textgreater{}} for birds, whose WoRMS
  taxonomy lags. See \hyperref[taxonomy]{Taxonomy} below.
\end{itemize}

\textbf{Provider UUIDs are released as typed columns where the provider
mints them.} They are not primary keys --- the string keys above are ---
but they are the join back to the provider's own database, and dropping
them would make that join impossible:

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{cruise.cruise\_uuid}} is NOAA/SWFSC's
  \texttt{CruiseId}, populated for every released cruise. It is a
  \textbf{public} join key, not an internal artefact.
\item
  \textbf{\texttt{sample.source\_uuid}} is the provider's identifier for
  \emph{that event} --- SWFSC's \texttt{site\_uuid} on a site row,
  \texttt{tow\_uuid} on a tow, \texttt{net\_uuid} on a net --- and is
  NULL for the datasets whose sources mint no UUID (15 of 16 do not).
\item
  \textbf{\texttt{sample.station\_uuid}} is the SWFSC station occupation
  an event belongs to, resolved in the release, with
  \texttt{station\_uuid\_method} saying how (the event's own site, its
  parent's, a match on \texttt{(cruise\_key,\ site\_key,\ order\_occ)},
  or the single ichthyoplankton occupation within 24 hours).
\end{itemize}

\texttt{\_source\_*} provenance columns --- the wrangling-time record of
which source file and row a value came from --- are a different thing
entirely and \textbf{are stripped at the freeze}; they never reach a
release.

All three columns ship since v2026.09.04; \texttt{metadata.json} for the
release you are reading, or the
\href{https://calcofi.io/db-schema/}{schema explorer}, lists them.

\textbf{The one sequential integer key the release mints is
\texttt{root\_id}}, on \texttt{sample\_root}: a dense integer for each
root sampling event (a \texttt{sample} row with no parent), numbered
deterministically so a rebuild reproduces it. \texttt{obs\_bio} and
\texttt{obs\_env} carry it so a browser can join observations to their
event without the string key.

hydrography, CTD casts, DIC, underway meteorology, seabird and mammal

ingest notebook (the generic shapes live in \texttt{calcofi4db}), so

\subsection{\texorpdfstring{What the release publishes:
\texttt{obs\_bio} + \texttt{obs\_env}, and \texttt{obs} as a
view}{What the release publishes: obs\_bio + obs\_env, and obs as a view}}\label{what-the-release-publishes-obs_bio-obs_env-and-obs-as-a-view}

The assembly grain is \texttt{obs}; what the \textbf{release} publishes
is the pair cut from it, because the questions consumers ask are shaped
differently for the two realms:

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{obs\_bio}} --- one object, the bio realm, with the
  gear and effort of the row's \emph{own} sampling event inline
  (\texttt{tow\_type}, \texttt{std\_haul\_factor},
  \texttt{prop\_sorted}, \texttt{volume\_sampled\_m3}) and the two
  standardized densities derived once (\texttt{density\_per\_10m2},
  \texttt{density\_per\_1000m3}) plus \texttt{effort\_class}. One taxon
  question = one file.
\item
  \textbf{\texttt{obs\_env}} --- one object \textbf{per
  \texttt{measurement\_type}}. One variable = one small fetch, which is
  what a browser-side reader (DuckDB-WASM cannot list a directory; the
  catalog gives it an explicit file list) actually needs.
\end{itemize}

Each is a strict superset of \texttt{obs} under a name mapping ---
\texttt{realm} is implied by which table you read, and \texttt{value} is
\texttt{measurement\_value} --- and \textbf{\texttt{obs} itself is a
view} the catalog carries (\texttt{catalog.json} → \texttt{views.obs}),
a \texttt{UNION\ ALL} over the pair under \texttt{obs}'s original column
names. \texttt{calcofi4r::cc\_get\_db()}, \texttt{calcofi4py} and the
query site create it from the catalog, so \texttt{FROM\ obs} keeps
working. Two consequences worth knowing:

\begin{itemize}
\tightlist
\item
  The release \textbf{proves} the pair reproduces \texttt{obs} before it
  freezes --- row counts, distinct \texttt{obs\_id}s and a hash
  signature of every column, per realm × dataset. The one allowed
  difference is a \emph{depth fallback}: a bio row with no depth of its
  own carries its tow's span.
\item
  \texttt{obs}'s physical objects still ship for one release, marked
  \texttt{deprecated} in the catalog with
  \texttt{replaced\_by:\ {[}"obs\_bio",\ "obs\_env"{]}}. \textbf{Migrate
  to the pair} --- a consumer reading the view needs no change, a
  consumer building a path to \texttt{obs.parquet} does.
\end{itemize}

Do not rename \texttt{value}, \texttt{root\_id} or \texttt{hex7} on the
pair; new columns are appended and the view maps names, so consumers
never have to.

\subsection{Shared reference tables}\label{shared-reference-tables}

\texttt{cruise} (one row per cruise, with \texttt{cruise\_uuid}, the
ship, and the observed \texttt{date\_min}/\texttt{date\_max} span that
keys every other dataset's events), \texttt{ship}, \texttt{grid} (the
CalCOFI station grid, materialized deterministically from
\texttt{calcofi4r::cc\_grid}), \texttt{spatial} +
\texttt{spatial\_attribute} (boundary layers), \texttt{sample\_spatial}
(the sample→layer memberships), \texttt{region}, \texttt{lookup},
\texttt{dataset} (one row per released dataset, with its measured
coverage and its citation), \texttt{measurement\_type} (the measurement
vocabulary, below) and \texttt{climatology}.

\textbf{\texttt{climatology} is the one baseline every anomaly
subtracts.} Until 2026-08-31 three products each computed their own and
the same section read +1.4 °C in one and \textasciitilde0 in another. It
is a plain mean per dataset × \texttt{grid\_key} × \textbf{calendar
month} × 10 m depth bin × measurement type over \textbf{1993--2013},
kept only where ≥ 3 distinct cruises contribute, with the window stamped
on every row. A cast's anomaly is its value minus the cell of \emph{its
own} calendar month; pooling months produces a seasonal-cycle map, not
an anomaly.

\subsection{Taxonomy}\label{taxonomy}

Three shared tables replace the \textasciitilde7 per-dataset taxon
tables:

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{taxon}} --- one row per taxon: \texttt{taxon\_key}
  (\texttt{worms:\textless{}AphiaID\textgreater{}}, or
  \texttt{itis:\textless{}TSN\textgreater{}} when the taxon's class is
  \textbf{Aves}, because WoRMS bird taxonomy lags), the cross-reference
  ids (\texttt{worms\_id}, \texttt{itis\_id}, \texttt{gbif\_id}),
  \texttt{parent\_taxon\_key}, \texttt{rank} and \texttt{rank\_order},
  the flattened lineage (\texttt{kingdom}, \texttt{phylum},
  \texttt{class}, \texttt{order\_taxon}, \texttt{family}),
  \texttt{scientific\_name}, \texttt{common\_name}, and
  \texttt{taxonomic\_status} \textbf{with} \texttt{status\_checked} ---
  read the two together; a status with no check date is not a fact.
\item
  \textbf{\texttt{dataset\_taxon}} --- the per-dataset vocabulary →
  \texttt{taxon\_key} crosswalk. \texttt{obs} resolves its
  \texttt{taxon\_key} by joining this on
  \texttt{(dataset\_key,\ ds\_taxa\_code)}, and
  \texttt{ds\_source\_json} records whatever ids the \emph{source}
  itself supplied, so the source and the authority can be audited
  against each other.
\item
  \textbf{\texttt{taxon\_group}} --- groupings for rollups.
\end{itemize}

Two distinctions that cost real data before they were written down.
\textbf{The key authority and the cross-reference columns are different
questions}: a bird keys \texttt{itis:} \emph{and} carries a
\texttt{worms\_id}, because a consumer joining on \texttt{worms\_id}
would otherwise match zero seabirds. And \textbf{a key must be an
accepted id} while a cross-reference is whatever the authority links ---
a deprecated TSN is re-keyed onto its accepted successor and the event
is recorded in \texttt{taxon.notes}.

When asserting lineage coverage, \textbf{split by rank position}:
\texttt{family} is legitimately NULL above family rank, and
\texttt{kingdom} is NULL for \texttt{worms:1} \emph{Biota}. A blanket
non-NULL assertion is wrong, and someone will ``fix'' it by inventing
data.

\subsection{Quality flags reach consumers only if consumers apply
them}\label{quality-flags-reach-consumers-only-if-consumers-apply-them}

\texttt{obs.measurement\_qual} is \textbf{each dataset's own vocabulary,
uninterpreted} --- bottle 6 = ok-from-CTD, 8 = suspect, 9 = missing; CTD
1/2 = use primary/secondary sensor, 8 = questionable, 9 = bad; DIC
follows WOCE (2 good, 3 questionable, 4 bad, 9 missing). The registry is
\texttt{metadata/measurement\_qual.csv} in the workflows repo and it
ships in \texttt{metadata.json}.

In August 2026 a 2.18 ml/L oxygen spike at 1,144 m turned out to be a
bottle flagged suspect in the source \textbf{since 1955} --- it reached
a plotted app because no consumer filtered on the column. There is now
one predicate per language --- \texttt{calcofi4r::cc\_qual\_ok\_sql()},
\texttt{calcofi4py.qual\_ok\_sql()}, the query site's
\texttt{qualOkSQL()} --- NULL-safe, so an unflagged row is kept.
\textbf{Apply it.} A value with a flag you do not read is not a value
you can trust.

\subsection{Depth is a coordinate, and it is bounded as
one}\label{depth-is-a-coordinate-and-it-is-bounded-as-one}

Every released depth is finite, non-negative and no deeper than
\textbf{6,500 m}, on \texttt{obs}, on \texttt{sample} and on the
supplemental tables; a violation fails the release rather than shipping.
Separately, \texttt{sample.seafloor\_depth\_m} carries the GEBCO 2025
sea-floor depth at the sample's position (positive down, 0 on land, NULL
outside the raster) so a consumer can judge a deep sample without
fetching a raster. Where a sample's deepest attributed depth exceeds the
deepest GEBCO cell near it, that is \textbf{reported and ratcheted,
never deleted}: nearly all such cases are minute-rounded 1949--1975
positions on slopes and canyons --- the measurement is fine, the place
is imprecise.

\section{Integrated database ingestion
strategy}\label{integrated-database-ingestion-strategy}

\subsection{Overview}\label{overview}

The integrated database is built by the
\href{https://github.com/CalCOFI/workflows}{\texttt{CalCOFI/workflows}}
pipeline: one \texttt{ingest\_\{provider\}\_\{dataset\}.qmd} notebook
per dataset (orchestrated by \texttt{targets}, engine functions in
\href{https://github.com/CalCOFI/calcofi4db}{\texttt{calcofi4db}})
writes Parquet shards plus JSON sidecars; \texttt{release\_database.qmd}
assembles them in an in-memory DuckDB, validates, and freezes a
versioned, immutable \textbf{release} on public Google Cloud Storage
(next section). Consumers --- the apps,
\texttt{calcofi4r::cc\_get\_db()}, the
\href{https://calcofi.io/db-schema/}{schema} and
\href{https://calcofi.io/db-query/}{query} sites --- read the release as
Parquet over HTTPS with no credentials.

Alongside the releases, a \textbf{PostgreSQL} database
(\texttt{calcofi}, PostgreSQL 18 + PostGIS 3.6 on the CalCOFI server) is
the \emph{working}, multi-user store for the CTD team's QA/QC: originals
loaded verbatim and immutable, a flag/proposal ledger beside them,
derived products on top. It is private and reached over SSH --- see
\href{server-access.qmd}{Server Access}. DuckDB's \texttt{postgres}
extension joins the two worlds in one query
(\texttt{calcofi4r::cc\_pg\_attach()}). (An earlier design ran the whole
database in PostgreSQL with \texttt{dev}/\texttt{prod} schemas and a
single \texttt{create\_db.qmd}; that is superseded and only the legacy
\texttt{gis} database remains, behind tile.calcofi.io.)

\subsection{Release versioning}\label{release-versioning}

Each rendered \texttt{release\_database.qmd} writes a frozen, immutable
release to \texttt{gs://calcofi-db/ducklake/releases/\{version\}/} where
\texttt{version} is \texttt{vYYYY.MM.DD}. The release directory holds
the \textbf{sidecars} --- the complete record of what the release is ---
and the \texttt{catalog.json} among them is the data-access contract:
consumers resolve every table through it
(\hyperref[where-the-data-lives]{Data Access}) rather than building a
path.

\begin{itemize}
\tightlist
\item
  \texttt{catalog.json} --- structural manifest: \texttt{version},
  \texttt{release\_date}, \texttt{total\_rows} / \texttt{total\_size},
  and per table \texttt{name}, \texttt{rows}, \texttt{partitioned},
  \texttt{supplemental}. From the v2026.09 releases it is
  \textbf{content-addressed} (\texttt{layout:\ "canonical"}, plus the
  \texttt{writer} settings --- compression, row-group size --- that make
  the bytes reproducible): each table carries \texttt{content\_hash} (a
  whole-table signature), \texttt{compat\_path} (its legacy per-release
  path) and \texttt{objects{[}{]}} --- one object for a single-file
  table, one per partition for a partitioned one --- each with a
  bucket-relative \texttt{path}
  (\texttt{ducklake/tables/\{table\}/\{content\_hash\}/\{table\}.parquet},
  or
  \texttt{ducklake/tables/\{table\}/\{col\}=\{value\}/\{hash\}/data\_0.parquet}),
  \texttt{bytes}, \texttt{sha256}, \texttt{content\_hash},
  \texttt{since} (the first version that shipped this exact object), its
  own \texttt{compat\_path} and, for a partition, \texttt{partition\_by}
  / \texttt{partition\_value}. A partitioned table may also publish a
  whole-table \textbf{twin} --- the one object without
  \texttt{partition\_by} (\texttt{obs} does) --- for https-only readers;
  it is read \emph{instead of} the partitions, never alongside them.
  Objects are immutable and shared between versions, so \texttt{since}
  is the per-table ``what changed'';
  \texttt{calcofi4r::cc\_release\_sources()} and
  \texttt{calcofi4py.release\_sources()} are the resolvers (the twin
  comes back as \texttt{single\_file}, excluded from \texttt{urls}).
\item
  \texttt{relationships.json} --- primary keys and foreign keys
\item
  \texttt{metadata.json} --- table and column descriptions, units,
  dataset block, measurement-type registry
\item
  \texttt{RELEASE\_NOTES.md} --- this version's section of
  \texttt{RELEASES.md} plus a generated appendix (tables and rows from
  \texttt{catalog.json}, datasets, the consumer-contract result, package
  versions)
\item
  \texttt{parquet/} --- the legacy per-release copy of the tables
  (single \texttt{.parquet} or hive-partitioned directories). Kept only
  for the promoted version, its predecessor and the
  \textbf{consolidated} versions; elsewhere it is removed by archive
  thinning (\texttt{metadata/release\_policy.yml} in
  \href{https://github.com/CalCOFI/workflows}{\texttt{CalCOFI/workflows}},
  applied by \texttt{scripts/thin\_releases.R}), while the sidecars
  stay.
\end{itemize}

Bucket-level, under \texttt{releases/}: \texttt{latest.txt} names the
promoted version (promoted only after \texttt{test\_release.qmd}'s
consumer-contract suite passes); \texttt{versions.json} lists every
release --- \texttt{version}, \texttt{release\_date}, \texttt{tables},
\texttt{total\_rows}, \texttt{size\_mb} --- with
\texttt{consolidated:\ true} on the milestone versions
(\texttt{v2026.04.08}, \texttt{v2026.05.14}, \texttt{v2026.06.26},
\texttt{v2026.07.17}, \texttt{v2026.08.14}, \texttt{v2026.08.25}) and
\texttt{retired:\ \{retired\_utc,\ to,\ reason\}} on a thinned one,
\texttt{to} being the consolidated version to use instead; and
\texttt{RELEASES.md} is the running changelog across versions, newest
first, with \texttt{\#\ Unreleased} collecting changes until the next
cut.

\subsection{Coverage is measured, never
asserted}\label{coverage-is-measured-never-asserted}

A dataset's temporal and spatial extent is \textbf{measured from the
assembled data at release time} ---
\texttt{coverage\_temporal\_observed},
\texttt{coverage\_spatial\_observed} and \texttt{coverage\_bbox} in
\texttt{metadata.json}, and the corresponding columns on the released
\texttt{dataset} table. Nothing hand-writes an extent.

This is not pedantry. A hand-written extent is authored once while the
data grows underneath it: at \texttt{v2026.08.06} seven of fifteen
datasets were wrong --- one claimed data through 2021-05 that ends
2015-04, three said ``present'' while stalling in 2019, 2022 and 2023.
Measurement is also honest about what it finds, which is how two
coordinate bugs surfaced that the prose had hidden (a dropped minus sign
putting a dataset at 124.9° \textbf{E}, and a dataset reaching latitude
\texttt{0.0}). One dataset asserts its temporal half and says why in a
comment: it is region-pooled and has no datetimes at all.

\subsection{Citation and licence are a contract, and they are
checked}\label{citation-and-licence-are-a-contract-and-they-are-checked}

Every dataset carries \texttt{citation\_main}, \texttt{license},
\texttt{doi}, \texttt{acknowledgement} and \texttt{contact} in its
\texttt{dataset\_meta.yml} sidecar, and these are \textbf{checked, not
trusted} --- by the workflows index build and again by the release. A
citation needs a year and a locator; \texttt{license} must be an active
id in \texttt{license.csv} (\texttt{custom} requires a
\texttt{license\_url}; \texttt{unknown} or empty fails unless a provider
question is open on that field); a \texttt{doi} is stored bare and must
resolve. The check also asks the source's own authority --- EDI's cite
service, NCEI's ``Cite as'', an ERDDAP \texttt{.das}, DataCite ---
caches the answer, and \textbf{reports drift without ever writing into
the notebook}: the author's string is the record.

\texttt{source\_accessed} is measured, not authored. And the release
cites itself: \texttt{catalog.json} carries a \texttt{citation}, a
\texttt{concept\_doi} and, once minted, the version \texttt{doi}; the
release notes open with ``How to cite''; \texttt{CITATION.cff} and
\texttt{.zenodo.json} are generated from the same source.

\begin{verbatim}
CalCOFI (2026). CalCOFI Integrated Database, release v2026.09.06 [Data set].
Scripps Institution of Oceanography, NOAA Fisheries, and California Department
of Fish and Wildlife. https://doi.org/10.5281/zenodo.22514953
\end{verbatim}

(That is the release promoted as this page was written; the current one
is in \texttt{catalog.json} and on \href{cite.qmd}{Cite This Data}.)

\textbf{When you use these data, cite the release \emph{and} the source
datasets you used.} The release \texttt{dataset} table carries each
source's own \texttt{citation\_main}, \texttt{license}, \texttt{doi} and
\texttt{acknowledgement} for exactly this purpose --- one row per
dataset, so a query that touched \texttt{dataset\_key} already knows
whom to credit.

\subsection{Publishing to portals}\label{publishing-to-portals}

Workflows in \texttt{workflows/publish\_to-*.qmd} push selected tables
to external portals --- ERDDAP, EDI, OBIS --- and write netCDF for the
archives. They read the release \texttt{catalog.json} and
\texttt{metadata.json} to assemble Ecological Metadata Language (EML),
ERDDAP \texttt{datasets.xml} entries and netCDF attributes, so a
description written once in a metadata registry reaches every portal
without re-keying, and so no publish notebook builds a parquet path by
hand.

The netCDF, ERDDAP, EDI and OBIS publishers are all \textbf{generic} ---
parameterised by dataset, driven by the release; the OBIS one
(\texttt{publish\_to-obis.qmd}, 2026-09-05) retired the per-dataset
ichthyoplankton notebook. See
\hyperref[darwin-core-obis-env-data-mapping]{Darwin Core / OBIS ENV-DATA
mapping} for what it reads, and \hyperref[obis]{Portals} for the
publishing steps.

\textbf{ERDDAP} (\texttt{publish\_to-erddap.qmd}) discovers one config
block per \texttt{dataset\_key} from what the core actually holds,
rather than a hand-maintained table list, and executes every view
against the real release before writing its XML. Since the pre-release
plan D-S1/D-S3 (2026-09) the \texttt{\{dataset\_key\}} observation grain
reads \texttt{obs\_bio} (bio datasets) or \texttt{obs\_env} (env
datasets) through the release catalog
(\texttt{calcofi4r::cc\_release\_sources()}) --- never a hand-built
\texttt{releases/\{v\}/parquet} path --- carrying the sample's own gear
and effort (\texttt{tow\_type}, \texttt{std\_haul\_factor},
\texttt{prop\_sorted}, \texttt{volume\_sampled\_m3}) and the two
canonical densities (\texttt{density\_per\_10m2},
\texttt{density\_per\_1000m3}, \texttt{effort\_class}) inline, plus
\texttt{flag\_values}/\texttt{flag\_meanings} on
\texttt{measurement\_qual} from \texttt{metadata/measurement\_qual.csv}.
A release cut before D-S1 (no \texttt{obs\_bio}/\texttt{obs\_env} in its
catalog) falls back to the deprecated \texttt{obs} objects, with no
effort/density columns.

\subsection{An id is filled only on an exact
match}\label{an-id-is-filled-only-on-an-exact-match}

\textbf{Empty means ``no concept in the vocabulary says exactly this'',
never ``nobody looked.''} An id is written only when every facet the
concept states --- quantity, matrix, phase, method --- is something the
registry or the dataset's documented protocol actually supplies. A
\emph{generic} concept is an exact match at coarser specificity: NERC
P01 \texttt{TEMPPR01}, \emph{Temperature of the water body}, is exactly
what a QC'd bottle temperature is. A concept that adds a facet nobody
recorded is not: \texttt{IRRDUV01} pins PAR to a cosine-collector
radiometer, which no CalCOFI metadata states, so PAR has no id.

Filling an id you are not sure of is worse than leaving it empty. An
empty \texttt{measurementTypeID} is a portal record that says ``this
measurement is not mapped''; a wrong one is a record that confidently
says the wrong thing, at an aggregator that will never ask.

\subsection{Three caveats for anyone building an
export}\label{three-caveats-for-anyone-building-an-export}

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{obs} is positive-only for ichthyoplankton.} A tow that
  was sorted and found nothing has \textbf{no row}, so
  \texttt{occurrenceStatus\ =\ "absent"} cannot be derived from zero
  values. Absences come from the sampling events (\texttt{sample}, root
  rows) minus the taxa observed on them --- and a surveyed year with no
  positives is indistinguishable from an unsurveyed year if you count
  rows instead of events.
\item
  \textbf{\texttt{organismQuantityType} is the whole meaning of the
  number.} Areal (individuals per 10 m², from an oblique or vertical tow
  standardized by the haul factor) and volumetric (individuals per 1000
  m³, from a surface Manta tow or any tow with a filtered volume) are
  \textbf{not interconvertible} without an integrated depth and a
  vertical-distribution assumption. Publish the denominator with the
  number, never a bare count.
\item
  \textbf{Two \texttt{life\_stage} values are not life stages.}
  Euphausiid \texttt{damaged} marks specimens too damaged to stage
  (\texttt{occurrenceRemarks}), and ichthyoplankton \texttt{invert} is a
  provenance flag for the merged invertebrate counts.
  \texttt{metadata/life\_stage.csv} says so per value; do not pass
  either through as \texttt{lifeStage}.
\end{itemize}

The generic \texttt{publish\_to-obis.qmd} over the core reads exactly
these registries; it replaced the per-dataset ichthyoplankton notebook
on 2026-09-05 (see \hyperref[obis]{Portals}).

\section{Spatial Tips}\label{spatial-tips}

\begin{itemize}
\item
  Use
  \href{https://postgis.net/docs/ST_Subdivide.html}{\texttt{ST\_Subdivide()}}
  when running spatial joins on large polygons.
\item
  \textbf{All released geometry is tagged \texttt{EPSG:4326}},
  normalized immediately before the freeze. This matters because
  \texttt{ST\_Point(lon,\ lat)} tags \texttt{OGC:CRS84} while
  \texttt{ST\_Read()} over GeoJSON tags \texttt{EPSG:4326} --- the same
  WGS 84 longitude/latitude --- and \textbf{DuckDB refuses
  \texttt{ST\_Intersects} across differing tags}. If you build geometry
  on one side of a join, tag both sides; do not coerce one to match the
  other, or the next release will break you.
\item
  \textbf{\texttt{NaN} is not \texttt{NULL}, and it corrupts spatial
  queries beyond its own row.} A \texttt{NaN} coordinate survives
  \texttt{IS\ NOT\ NULL}, and \texttt{ST\_Point(NaN,\ NaN)} returns a
  real, non-NULL geometry that survives \texttt{geom\ IS\ NOT\ NULL}
  too. Worse, its presence makes \texttt{ST\_Intersects} return
  \textbf{different counts at different thread counts}, dropping valid,
  unrelated pairs. The release normalizes \texttt{NaN}/\texttt{Inf} to
  \texttt{NULL} before minting geometry --- but if you build your own,
  test \texttt{isnan()} and \texttt{isinf()} explicitly.
\end{itemize}

\begin{itemize}
\tightlist
\item

\section{\texorpdfstring{Questions, and what \emph{proposed}
means}{Questions, and what proposed means}}\label{questions-and-what-proposed-means}

Every question we have for a dataset's owner is a row in
\texttt{metadata/\{provider\}/\{dataset\}/questions.csv} (see
\hyperref[database]{the registries}) and in that dataset's Sheet tab. A
row has a short label (\texttt{Q07}), the question, the context we
already know, a priority, and a \texttt{status}:

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{open}} --- we need an answer we do not have.
\item
  \textbf{\texttt{proposed}} --- we have already built or reasoned an
  answer and want it confirmed; the \texttt{proposed\_answer} column
  holds it. Most rows are \texttt{proposed}, so a provider approves a
  solution rather than being handed a problem.
\item
  \textbf{\texttt{answered}} and \textbf{\texttt{wontfix}} --- closed,
  with the answer kept beside the question.
\end{itemize}

Questions reach a provider through the Sheet and, when a batch is ready,
through one email drafted from the same rows. Answers come back the same
way: the data team pulls the Sheet, the four answer columns are
validated and written into \texttt{questions.csv} in one commit, and the
next release carries whatever changed.

\section{What happens after you edit}\label{what-happens-after-you-edit}

Nothing happens on the Sheet itself. The data team runs a sync
(\texttt{push} to regenerate the tabs from git, \texttt{pull} to bring
edits back; both are dry runs until told otherwise), which rewrites only
the changed values in the sidecar and leaves its history and comments
intact. The next release --- cut every few weeks, each with its own DOI
--- then regenerates every surface from the record:

\section{A new dataset, end to end}\label{a-new-dataset-end-to-end}

Bringing a dataset in is a loop of five steps with a person at every
hand-off:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Explore} --- profile the source (columns, coverage, keys,
  provider), and seed the first questions from what the profile cannot
  answer.
\item
  \textbf{Metadata} --- map the source's fields onto the shared field
  dictionary and measurement vocabulary; register the dataset's key,
  category and descriptive sidecar.
\item
  \textbf{Ingest} --- a notebook
  (\texttt{ingest\_\{provider\}\_\{dataset\}.qmd}) turns the source into
  the core tables, with the provider's own identifiers kept as columns
  and the questions section at the end.
\item
  \textbf{Validate} --- keys, ranges, taxa and coverage are checked;
  every finding is either fixed or becomes a \texttt{proposed} question.
\item
  \textbf{Release} --- the dataset joins the next frozen release, gets
  its page, its EML and STAC records, and its rows in the apps.
\end{enumerate}

A dataset can stop after step 3 with \texttt{in\_release:\ false} while
its questions are open. That is normal, and it is what the holdings
triage board is for: a holding's \texttt{next\_step} names which of
these steps it is waiting on and who owns it.

\chapter{Data Access}\label{data-access}

CalCOFI \hyperref[database]{database} releases are published as
\textbf{Parquet} files on a public Google Cloud Storage (GCS) bucket.
You can query them directly with \href{https://duckdb.org}{DuckDB} ---
from R, Python, the DuckDB CLI, or any DuckDB client --- with \textbf{no
credentials, no API server, and no full download}. DuckDB reads only the
columns and row groups a query actually touches, straight over HTTPS.

This page covers querying the release Parquet directly. For
convenience-wrapped biological ↔ environmental matching, see
\href{helpers.qmd}{Matching Helpers}. Looking for a particular dataset
rather than a query? Every dataset has its own page at
\href{https://calcofi.io/datasets/}{calcofi.io/datasets/\{dataset\_key\}/}
--- coverage, every place it can be reached (this page's Parquet
included), its citation and its provider --- see
\href{portals.qmd}{Portals}.

The releases are read-only snapshots. The CTD team's \emph{working}
database --- multi-user PostgreSQL on the CalCOFI server, private,
reached over SSH --- is described in \href{server-access.qmd}{Server
Access}, including how to join it with the releases from DuckDB.

\section{Where the data lives}\label{where-the-data-lives}

A release is a versioned folder of \textbf{sidecars} --- the record of
what the release is --- and its tables are Parquet \textbf{objects} that
the release's \texttt{catalog.json} points at:

\begin{verbatim}
gs://calcofi-db/ducklake/
├── releases/
│   ├── latest.txt              # the promoted version, e.g. v2026.08.25
│   ├── versions.json           # every version: date, tables, rows; consolidated / retired
│   ├── RELEASES.md             # what changed between versions and why, newest first
│   └── {version}/
│       ├── catalog.json        # table list, rows, partitioned/supplemental flags,
│       │                       #   and objects[] — where each table's bytes live
│       ├── relationships.json  # primary keys + foreign keys
│       ├── metadata.json       # table/column descriptions, units, datasets, measurement types
│       ├── RELEASE_NOTES.md    # this version's RELEASES.md section + a generated appendix
│       └── parquet/            # legacy per-release copy — promoted + consolidated versions only
│           ├── {table}.parquet
│           └── {table}/dataset_key=.../*.parquet
└── tables/                     # content-addressed objects, from the v2026.09 releases
    ├── {table}/{content_hash}/{table}.parquet
    └── {table}/{col}={value}/{content_hash}/data_0.parquet
\end{verbatim}

\begin{itemize}
\tightlist
\item
  Public HTTPS root of the bucket:
  \texttt{https://storage.googleapis.com/calcofi-db/} --- every
  \texttt{path} in a catalog is relative to it.
  \texttt{https://storage.calcofi.io/calcofi-db/} serves the same bucket
  and redirects a legacy \texttt{releases/\{version\}/parquet/…} URL to
  the canonical object where one still exists.
\item
  The promoted version is at
  \href{https://storage.googleapis.com/calcofi-db/ducklake/releases/latest.txt}{\texttt{releases/latest.txt}};
  the table list --- and where each table's bytes live --- at
  \texttt{releases/\{version\}/catalog.json}.
\item
  \textbf{Resolve a table through the catalog; never build a
  \texttt{parquet/} path by hand.} From the v2026.09 releases each table
  entry in \texttt{catalog.json} carries \texttt{objects{[}{]}} --- one
  object for a single-file table, one per partition for a partitioned
  one --- with a bucket-relative \texttt{path}, \texttt{bytes},
  \texttt{sha256}, \texttt{content\_hash}, \texttt{since} (the first
  version that shipped that exact object) and its own
  \texttt{compat\_path} (the legacy per-release path of that one file).
  Objects are immutable and shared between versions: a release that
  changed three tables shares every other object with the release before
  it, so \texttt{since} is the per-table ``what changed''. The legacy
  \texttt{releases/\{version\}/parquet/\{table\}.parquet} copy remains
  only for the promoted version and the consolidated ones (see
  \hyperref[sec-versions]{Versions}). The packages' resolvers ---
  \texttt{calcofi4r::cc\_release\_sources()},
  \texttt{calcofi4py.release\_sources()} --- turn a catalog entry into
  URLs for any version, including those before v2026.09.
\item
  Most tables are \textbf{single-file}. \texttt{obs} and the
  supplemental \texttt{obs\_ctd\_full} / \texttt{obs\_mets\_full} are
  \textbf{hive-partitioned} by \texttt{dataset\_key}
  (\texttt{catalog.json} flags these with
  \texttt{"partitioned":\ true}); a partition object's \texttt{path}
  carries its \texttt{dataset\_key=…} segment, so
  \texttt{hive\_partitioning\ =\ true} recovers the column. Supplemental
  tables (\texttt{"supplemental":\ true}) are hosted and cataloged but
  excluded from \texttt{cc\_get\_db()} by default ---
  \texttt{obs\_ctd\_full} alone is \textasciitilde270 M rows.
\item
  To \textbf{see what's in each table} before writing a query, open the
  \href{https://calcofi.io/db-schema/}{\textbf{CalCOFI Schema explorer}}
  --- ERD, sortable tables/columns with units and descriptions, dataset
  provenance, and the canonical measurement-type registry, all reading
  the same \texttt{metadata.json} sidecar.
\end{itemize}

\section{Versions}\label{sec-versions}

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{latest} vs pinned.} \texttt{latest.txt} names the
  \emph{promoted} version --- a release is promoted only after its
  consumer-contract query suite passes, so \texttt{latest} is safe to
  follow interactively and is what \texttt{cc\_get\_db()} defaults to.
  Anything that must be reproducible --- a paper, an app build, a
  download bundle --- pins a \texttt{vYYYY.MM.DD}. Releases are
  immutable: the same version always returns the same rows.
\item
  \textbf{Consolidated vs retired.} Every version keeps its sidecars and
  notes, but only some keep their bytes. The \textbf{consolidated}
  versions (\texttt{"consolidated":\ true} in \texttt{versions.json})
  mark a schema or data milestone and keep their \texttt{parquet/} copy
  indefinitely --- \texttt{v2026.04.08} (last of the per-dataset
  schema), \texttt{v2026.05.14} (first \texttt{ctd\_thin}),
  \texttt{v2026.06.26} (zoodb and zooscan enter), \texttt{v2026.07.17}
  (unified \texttt{taxon}), \texttt{v2026.08.14} (last before
  content-addressing) and \texttt{v2026.08.25} (\texttt{cruise\_key} by
  date span, depth ceiling, quality flags mapped) --- plus, always, the
  promoted version and its predecessor. Every other version is
  \textbf{retired} by archive thinning once it is neither: its
  \texttt{versions.json} entry gains
  \texttt{retired:\ \{retired\_utc,\ to,\ reason\}}, where \texttt{to}
  is the consolidated version to use instead, and
  \texttt{cc\_get\_db("v2026.08.10")} errors naming it rather than
  failing table by table on 404s. When you pin, pin a consolidated
  version.
\item
  \textbf{What changed.}
  \href{https://storage.googleapis.com/calcofi-db/ducklake/releases/RELEASES.md}{\texttt{RELEASES.md}}
  is the running changelog across versions --- one section per release,
  newest first, saying what was wrong, what is true now, and what it
  costs a consumer (\texttt{**Consumers:**} lines). Each version's
  \texttt{RELEASE\_NOTES.md} is its section plus a generated appendix
  (tables and rows, datasets, the consumer-contract result, package
  versions): \texttt{calcofi4r::cc\_release\_notes(version)} prints it,
  and \texttt{cc\_list\_versions()} /
  \texttt{calcofi4py.cc\_list\_versions()} list \texttt{versions.json}.
  Per table, \texttt{objects{[}{]}.since} in the catalog says which
  version last changed its bytes.
\end{itemize}

\section{Single-file tables}\label{single-file-tables}

A single-file table is one HTTPS URL handed to \texttt{read\_parquet()}.
Take it from the catalog (the packages do this for you, below); typed by
hand it must be a version whose \texttt{parquet/} copy is kept ---
\texttt{v2026.08.25} is consolidated, so this URL answers indefinitely:

\begin{Shaded}
\begin{Highlighting}[]
\KeywordTok{SELECT}\NormalTok{ taxon\_key, scientific\_name, common\_name, worms\_id, }\FunctionTok{rank}
\KeywordTok{FROM}\NormalTok{ read\_parquet(}\StringTok{\textquotesingle{}https://storage.googleapis.com/calcofi{-}db/ducklake/releases/v2026.08.25/parquet/taxon.parquet\textquotesingle{}}\NormalTok{)}
\KeywordTok{WHERE}\NormalTok{ scientific\_name }\OperatorTok{=} \StringTok{\textquotesingle{}Sardinops sagax\textquotesingle{}}\NormalTok{;}
\end{Highlighting}
\end{Shaded}

Joins work the same way --- name each table's URL. The core model is
small: \texttt{obs} holds one measured value per row (\texttt{realm} =
\texttt{bio} \textbar{} \texttt{env}) and points at the \texttt{sample}
it came from (\texttt{sample\_key}; \texttt{parent\_sample\_key} walks
net → tow → site and bottle → cast) and, for biology, at \texttt{taxon}
(\texttt{taxon\_key}); event-level effort such as
\texttt{std\_haul\_factor} is in \texttt{sample\_measurement}:

\begin{Shaded}
\begin{Highlighting}[]
\KeywordTok{SELECT}\NormalTok{ s.sample\_key, s.sample\_type, s.datetime, s.latitude, s.longitude,}
\NormalTok{       sm.measurement\_type, sm.measurement\_value}
\KeywordTok{FROM}\NormalTok{ read\_parquet(}\StringTok{\textquotesingle{}https://storage.googleapis.com/calcofi{-}db/ducklake/releases/v2026.08.25/parquet/sample.parquet\textquotesingle{}}\NormalTok{) s}
\KeywordTok{JOIN}\NormalTok{ read\_parquet(}\StringTok{\textquotesingle{}https://storage.googleapis.com/calcofi{-}db/ducklake/releases/v2026.08.25/parquet/sample\_measurement.parquet\textquotesingle{}}\NormalTok{) sm }\KeywordTok{ON}\NormalTok{ sm.sample\_key }\OperatorTok{=}\NormalTok{ s.sample\_key}
\KeywordTok{WHERE}\NormalTok{ s.dataset\_key }\OperatorTok{=} \StringTok{\textquotesingle{}swfsc\_ichthyo\textquotesingle{}}

\KeywordTok{LIMIT} \DecValTok{10}\NormalTok{;}
\end{Highlighting}
\end{Shaded}

\section{Hive-partitioned tables}\label{hive-partitioned-tables}

\texttt{obs} (and the supplemental \texttt{obs\_ctd\_full} /
\texttt{obs\_mets\_full}) is partitioned into one folder per
\texttt{dataset\_key}. From the v2026.09 releases the catalog lists each
partition as its own object, so a partitioned table is read as an
\textbf{explicit list of HTTPS URLs} --- \texttt{objects{[}{]}.path}
prefixed with the bucket root --- with
\texttt{hive\_partitioning\ =\ true} to recover \texttt{dataset\_key}
from the \texttt{dataset\_key=…} path segment. That runs in every
DuckDB, the browser included:

Because \texttt{dataset\_key} is the partition column, filtering on it
lets DuckDB \textbf{prune} whole partitions --- a single-dataset query
never opens the other files. Nobody types that list:
\texttt{calcofi4r::cc\_read\_parquet\_sql()} /
\texttt{calcofi4py.read\_parquet\_sql()} emit it from the catalog (next
sections).

A partitioned table may \textbf{also} publish one whole-table file --- a
single-file \textbf{twin} --- and \texttt{obs} does. In the catalog it
is the \texttt{objects{[}{]}} entry \emph{without}
\texttt{partition\_by}
(\texttt{ducklake/tables/obs/\{content\_hash\}/obs.parquet}); the
resolvers leave it out of \texttt{urls} and return it separately as
\texttt{single\_file} (\texttt{NA} / \texttt{None} for a table that has
none). It exists for https-only readers that cannot take a list ---
browser DuckDB-WASM, a \texttt{read\_parquet()} that wants one URL ---
which read \texttt{single\_file} \emph{instead of} the partition list.
Read one or the other, \textbf{never both}: the twin holds the same rows
as the partitions, so a query over both counts every row twice. The
price of the twin is partition pruning --- a \texttt{dataset\_key}
filter still works, but scans the one file. On releases before v2026.09
it is the plain per-release copy,
\texttt{…/releases/\{version\}/parquet/obs.parquet}:

\begin{Shaded}
\begin{Highlighting}[]

\section{Reproducibility}\label{reproducibility}

Because every query is plain SQL against immutable, versioned, public
Parquet, a CalCOFI result is \textbf{reproducible by anyone} --- pin the
\texttt{\{version\}} and re-run the SQL. Pin a
\hyperref[sec-versions]{consolidated} version: its bytes are kept
indefinitely, and a later release that shares an object with it shares
the same bytes.

The \href{https://app.calcofi.io/db-viz-hex}{Integrated App} builds on
this: its data \textbf{download bundle} ships a \texttt{query/} folder
alongside the data:

\begin{verbatim}
data/original/{bio,env}.csv          ← query/{bio,env}.sql
data/integrated/integrated_*.csv     ← query/integrated_*.sql
query/manifest.json                  release version, filters, GCS source URLs,
                                     per-file row counts + md5 checksums
query/REPRODUCE.md                   DuckDB-CLI / Python / R re-run snippets
\end{verbatim}

Each \texttt{*.sql} file is fully interpolated, GCS-URL-based, and
copy-paste runnable (prefixed with the \texttt{INSTALL}/\texttt{LOAD} it
needs). Re-run \texttt{query/integrated\_*.sql} in DuckDB and you get
back exactly the rows in the matching \texttt{.csv} --- the
\texttt{manifest.json} md5 checksums let you confirm it. The same SQL is
what \href{helpers.qmd}{\texttt{calcofi4r::cc\_match\_bio\_env()}}
executes and attaches as \texttt{attr(x,\ "sql")}, what the
browser-based \textbf{\href{https://calcofi.io/db-query/}{CalCOFI
Query}} generates as its \texttt{SQL} panel, and what a hand-written
query produces --- \textbf{a single source of truth across R, Python,
the CLI and JavaScript}.

\chapter{Cite This Data}\label{cite-this-data}

This is the \textbf{Data Sources \& Attribution} page --- the one answer
to ``how do I cite CalCOFI data?''. Every CalCOFI product points here
rather than restating it: the release itself has a citation, and every
dataset inside it carries its own --- checked against the source's own
authority, never invented (the attribution contract lives in
\href{https://github.com/CalCOFI/workflows/blob/main/CLAUDE.md}{CalCOFI/workflows}).

\begin{tcolorbox}[enhanced jigsaw, arc=.35mm, colback=white, left=2mm, leftrule=.75mm, titlerule=0mm, bottomrule=.15mm, colbacktitle=quarto-callout-important-color!10!white, colframe=quarto-callout-important-color-frame, rightrule=.15mm, title=\textcolor{quarto-callout-important-color}{\faExclamation}\hspace{0.5em}{Two things to cite, always}, breakable, opacityback=0, toptitle=1mm, toprule=.15mm, coltitle=black, bottomtitle=1mm, opacitybacktitle=0.6]

If your work touches the CalCOFI Integrated Database, cite
\textbf{both}: the release (the database as a whole --- the assembly,
the schema, the QA/QC) \emph{and} every individual dataset your analysis
actually used (the people who collected and curated the data). Citing
only the release erases the contributing datasets; citing only a dataset
erases the integration work that made it queryable alongside fifteen
others.

\end{tcolorbox}

\section{Step 2 --- your database password}\label{sec-pgpass}

Your PostgreSQL password was generated when the account was created and

never put the password in a script. Copy the \texttt{localhost} line

\section{Windows}

\texttt{C:\textbackslash{}Users\textbackslash{}\textless{}you\textgreater{}\textbackslash{}AppData\textbackslash{}Roaming\textbackslash{}postgresql\textbackslash{}pgpass.conf}).

\section{\texorpdfstring{The core engine:
\texttt{cc\_match\_bio\_env()}}{The core engine: cc\_match\_bio\_env()}}\label{the-core-engine-cc_match_bio_env}

The wrappers are thin shells over \texttt{cc\_match\_bio\_env()}, which
takes a \texttt{bio} and an \texttt{env} SQL \texttt{SELECT} string and
performs the match. Call it directly when you need a biological or
environmental side the wrappers don't cover (custom filters, a different
grouping, joining \texttt{bottle} to \texttt{cast\_condition}, \ldots):

\textbf{Contract.} \texttt{bio} must yield \texttt{bio\_id},
\texttt{bio\_datetime}, \texttt{bio\_lon}, \texttt{bio\_lat},
\texttt{bio\_value} (plus any descriptive columns, carried through as
grouping keys). \texttt{env} must yield exactly \texttt{env\_id},
\texttt{env\_datetime}, \texttt{env\_lon}, \texttt{env\_lat},
\texttt{env\_value}, \texttt{env\_depth\_m}, \texttt{measurement\_type}.
Both typically
\texttt{FROM\ read\_parquet(\textquotesingle{}https://…/\{table\}.parquet\textquotesingle{})}
so the emitted SQL stays portable.

\section{Parameters}\label{parameters}

\begin{itemize}
\tightlist
\item
  \textbf{\texttt{max\_dist\_km}, \texttt{max\_time\_hr}} --- the
  spatial and temporal match windows. Defaults are 2 km / 6 hr;
  \texttt{relax\_matching\ =\ TRUE} widens them to 5 km / 72 hr (an
  explicit value always wins). This replaces the old API's
  \texttt{relax\_matching} boolean.
\item
  \textbf{\texttt{join\_method}} --- how the environmental observations
  inside the window are reduced to one value per biological observation:

  \begin{itemize}
  \tightlist
  \item
    \texttt{"nearest\_time"} (default) --- keep the closest in time,
    average ties;
  \item
    \texttt{"nearest\_dist"} --- keep the closest in space, average
    ties;
  \item
    \texttt{"average"} --- average every observation in the window.
  \end{itemize}

  CalCOFI co-locates net tows and CTD casts, so in practice
  \texttt{nearest\_time} and \texttt{nearest\_dist} usually agree and
  \texttt{average} differs only slightly.
\item
  \textbf{\texttt{life\_stage}} (ichthyo wrappers) --- restrict to
  e.g.~\texttt{"larva"} or \texttt{"egg"}.
\item
  \textbf{\texttt{date\_min}, \texttt{date\_max}} --- bound the
  biological side by tow start date.
\item
  \textbf{\texttt{depth\_m\_min}, \texttt{depth\_m\_max}} --- bound the
  environmental bottle depths.
\item
  \textbf{\texttt{version}} --- a release string like
  \texttt{"v2026.05.14"}, or \texttt{"latest"}.
\end{itemize}

\chapter{Portals}\label{portals}

\section{Overview}\label{overview-1}

CalCOFI data is available through various portals, each serving
different purposes and user needs. Since 2026-09, every dataset ---
integrated into the database or still a holding --- also has one
calcofi.io page
(\href{https://calcofi.io/datasets/}{\texttt{/datasets/\{dataset\_key\}/}})
joining every endpoint it can be reached through: the release Parquet, a
CF netCDF, ERDDAP, and the archive or aggregator portals below, each
with its own publication status. That page, not this chapter, is now the
record --- the tables here are generated from the same registries the
page reads, so the two can never disagree.

\section{Data Flow}\label{data-flow}

While it would be ideal for CalCOFI data to be available through a
single portal, each portal has its strengths and limitations. The
diagram below is the flow as it runs today: what we author and observe
(left) becomes one record per dataset at release, that record generates
every surface a portal can read, and each portal or meta-portal is
pointed at one of those static files.

every downstream portal individually.

  \end{itemize}
\end{itemize}

\textbf{Publishing there is manual, in four steps}
(\texttt{publish\_to-edi.qmd}, generic per dataset; the package is built
from the release's own \texttt{eml/\{dataset\_key\}.xml} plus CSV
entities exported from the core --- for the bottle database three tables
totalling 2.1 GB plus the shared vocabulary table). (1) An EDI account
for the open \texttt{edi} scope, held by Erin, with Ben granted editor
access through the EML \texttt{access} element --- created once at
dashboard.edirepository.org. Every render already stages the package at
\texttt{gs://calcofi-db/publish/edi/\{dataset\_key\}/\{dataset\_key\}\_\{version\}/}
for review (the dataset page lists it as \emph{built, not deposited}).
(2) Set \texttt{EDI\_USER}/\texttt{EDI\_PASS} (or an EDI API key as
\texttt{EDI\_KEY}) wherever the pipeline runs and render the notebook:
PASTA \textbf{evaluate} runs automatically against \textbf{staging} and
the report lands beside the package; fix what it names and re-render.
(3) Once evaluate is clean, render with
\texttt{CALCOFI\_PUBLISH\_EDI=true} to \textbf{create} (or, on a later
release, \textbf{update}) the package against \textbf{production} ---
this mints a DOI and a \texttt{scope.identifier.revision}, recorded in
\texttt{metadata/edi\_packages.csv}. (4) Add the DOI back as an
\texttt{archive} row in \texttt{metadata/distribution.csv}
(\texttt{portal:\ edi}) and as the dataset's \texttt{doi} in its
\texttt{metadata/\{provider\}/\{dataset\}/dataset\_meta.yml}, so the
record and the citation carry it from the next release on. CCE-LTER's
\texttt{knb-lter-cce} packages stay theirs and are never republished.

\texttt{publish\_to-obis.qmd} writes
\texttt{data/darwincore/\{dataset\_key\}\_\{version\}.zip} and a
\texttt{\{dataset\_key\}\_manifest.json}, and stages both at
\texttt{gs://calcofi-db/publish/dwca/\{dataset\_key\}/} so a provider
--- and the dataset page, which lists the archive as \emph{built, not
deposited} --- can inspect the bundle before any upload; nothing in the
pipeline talks to a portal. CalCOFI has no IPT of its own --- the
resources live on the \textbf{OBIS-USA IPT}, \texttt{ipt-obis.gbif.us},
under Ben's login. Before a first upload, the OBIS records that already
cover the same source are listed (the notebook queries
\texttt{api.obis.org/v3/dataset} and prints the curated rows from
\texttt{metadata/distribution.csv}) and resolved \textbf{with their
owners}: a provider's own record is never duplicated, and a historical
CalCOFI record is retired or cross-referenced only with its owner's
agreement. Then: open (or create) the resource → upload the zip's files
as the source → map the Event core plus the Occurrence and
ExtendedMeasurementOrFact extensions exactly as \texttt{meta.xml}
describes them → publish a new version. Afterwards, record the OBIS
dataset id and the IPT resource id as \texttt{distribution.csv} rows
(\texttt{portal\ =\ obis} / \texttt{ipt}, \texttt{kind\ =\ archive}) and
stamp \texttt{uploaded\_utc} + \texttt{uploaded\_hash} into the
manifest. That last step is what makes a dataset page honest: the record
reports \texttt{built,\ not\ uploaded} / \texttt{published\ (vX)} /
\texttt{stale\ —\ data\ changed\ in\ vY} by comparing the uploaded hash
with the archive's own, so it says when an upload is due. Re-upload only
when the \texttt{content\_hash} changed --- it is deterministic over the
archive's CSV bytes.

\section{Metadata}\label{metadata}

The \href{https://eml.ecoinformatics.org/}{Ecological Metadata Language
(EML)} is the one metadata document CalCOFI's publishers share. Since

\texttt{eml/\{dataset\_key\}.xml}, built by
\texttt{calcofi4db::build\_eml()} directly from \texttt{datasets.json}

before it ships --- rather than each publish notebook typing its own
sampling methods, study extent and rights by hand. The Darwin Core
Archive OBIS publishing uses and an EDI data package both start from the
same document, so a provider correction to a dataset's abstract or
creators reaches every publisher at once.

\section{Meta-Portals}\label{meta-portals}

\subsection{Google Dataset Search}\label{google-dataset-search}

The JSON-LD metadata on every calcofi.io dataset page gets indexed by
\href{https://datasetsearch.research.google.com/search?query=calcofi}{Google
Dataset Search} through schema.org metadata. This ensures that CalCOFI
data is discoverable through Google search and other search engines.

\subsection{ODIS}\label{odis}

\textbf{Ocean Data Information System}

ODIS uses the same technology as Google Dataset Search (schema.org,

calcofi.io's generated
\href{https://calcofi.io/datasets/sitemap.xml}{\texttt{datasets/sitemap.xml}},
so a dataset's calcofi.io page is what \href{https://odis.org}{ODIS.org}

record from there.

calcofi.io publishes a
\href{https://calcofi.io/data.json}{\texttt{data.json}} (Project Open

the sitemap is --- one entry per public dataset, with its licence,
distributions and contact point. This is what a CKAN instance (data.gov,
a university's, CDFW's) harvests with no work on our side.

This federated approach ensures that CalCOFI data remains:

\begin{itemize}
\tightlist
\item
  Discoverable through multiple channels
\item
  Properly cited and attributed
\item
  Integrated with global ocean data systems
\end{itemize}

\section{Archive of record, per
dataset}\label{archive-of-record-per-dataset}

Every dataset has \textbf{one} portal that holds its citable,
DOI-bearing copy --- its archive of record --- and the others are either
aggregators and services that read from it or do not apply. The rule is
stated per dataset, in one sentence, in
\texttt{metadata/dataset\_status.csv}'s \texttt{publish\_policy} column
(CalCOFI/workflows), carried into \texttt{datasets.json} as
\texttt{status.publish\_policy} (calcofi4db ≥ 4.6.3) and shown on each
dataset page above its \emph{Archives \& portals} table. The rules
behind the sentences:

\begin{itemize}
\tightlist
\item
  \textbf{A provider's own archive is the archive of record, and is
  never republished.} The nine CCE-LTER-adjacent datasets live in
  \texttt{knb-lter-cce} on EDI (phyllosoma, phytoplankton, euphausiids,
  picoplankton, the Farallon bird and mammal census) or in CCE-LTER's
  DataZoo exports (ZooDB, ZooScan); DIC is NCEI accession 0301029; the
  mesopelagic fish and the Dungeness crab megalopae are UC San Diego
  Library deposits; CUFES is SWFSC's CoastWatch ERDDAP dataset.
\item
  \textbf{CalCOFI's own program datasets get an EDI package from the
  release} --- bottle, CTD casts, METS --- built by
  \texttt{publish\_to-edi.qmd} from \texttt{eml/\{dataset\_key\}.xml}
  and the release tables, staged at
  \texttt{gs://calcofi-db/publish/edi/} for review, deposited only with
  credentials and \texttt{CALCOFI\_PUBLISH\_EDI=true}. NCEI for these is
  planned through the SWFSC data manager.
\item
  \textbf{OBIS is the archive of record for occurrences of named taxa.}
  The SWFSC ichthyoplankton is published there (through the OBIS-USA
  IPT); every other biological dataset's Darwin Core Archive is built
  and staged at \texttt{gs://calcofi-db/publish/dwca/} each release, and
  its upload is the provider's call (planned). Environmental datasets do
  not apply.
\item
  \textbf{NCEI is the provider's to deposit for NOAA-collected data}
  (SWFSC's ichthyoplankton and CUFES), so it reads \texttt{n/a} on those
  rather than \texttt{planned}.
\item
  \textbf{Zenodo} holds the integrated database release itself, one DOI
  per version.
\end{itemize}

  \texttt{calcofi4py.cc\_datasets()} read the same

  \textbf{\hyperref[cite-this-data]{Cite This Data}} ---

  writing a query at all; each app's Sources panel links back to the

\subsection{1. Ingest --- A Versioned, Reproducible Integrated
Database}\label{ingest-a-versioned-reproducible-integrated-database}

The bulk of the period's effort went into the ingestion pipeline
(\texttt{workflows}) and its engine package (\texttt{calcofi4db}), which
together turn heterogeneous source files into a single, versioned
database.

\begin{itemize}
\item
  \textbf{All must-complete datasets ingested.} Building on bottle, fish
  eggs \& larvae (ichthyo), and CTD casts, the team added \textbf{DIC}
  (dissolved inorganic carbon), \textbf{phytoplankton} (Venrick, EDI
  \#28, region-pooled grain with WoRMS taxonomy), \textbf{lobster
  phyllosoma} (EDI \#33), \textbf{CUFES} (\#35),
  \textbf{euphausiids/krill}, \textbf{PIC zooplankton}, and \textbf{bird
  \& mammal census} data. Cephalopod/invertebrate counts were folded
  into the ichthyo dataset rather than maintained separately. Release
  \textbf{v2026.06.08} now spans \textbf{44 tables}.
\item
  \textbf{Frozen, reproducible releases (DuckLake + Parquet on GCS).}
  \texttt{release\_database.qmd} acts as the pipeline ``caboose'': it
  validates, freezes, and uploads each release to a Google Cloud Storage
  bucket as Parquet, with an auto-generated entity-relationship diagram
  and a \texttt{metadata.json} sidecar carrying full table/column
  descriptions, units, and data types. Nine releases were cut between
  March and June 2026.
\item
  \textbf{A hardened, well-keyed data model.} Identifiers were
  standardized on stable keys --- UUID-first source keys,
  \texttt{cruise\_key} as \texttt{YYYY-MM-NODC}, and
  \texttt{sta\_key\ →\ site\_key}. The CTD data --- by far the largest
  input --- was tamed with a new adaptively-thinned
  \textbf{\texttt{ctd\_thin}} table (5.5M rows / \textasciitilde258 MB,
  preserving inflections via Douglas-Peucker) replacing the 15+ GB raw
  measurement table as the headline product, and several duplicate-key
  and phantom-cruise bugs were fixed.
\item
  \textbf{\texttt{calcofi4db} formalized (v2.4 → v2.8).} New
  capabilities include content-hash deduplication of Parquet uploads
  (ignoring provenance columns), YAML-authoritative dataset metadata,
  native \texttt{GEOMETRY} storage with \texttt{ST\_Hilbert} spatial
  ordering, dependency VIEWs, and server-side GCS copy --- which
  together cut a full pipeline run from 60+ minutes to \textasciitilde4
  minutes. A reusable set of \textbf{Claude Code ingest skills} (explore
  → generate-metadata → ingest → validate) and \textbf{cross-dataset
  match helpers} now make adding a new dataset largely turnkey.
\item
  \textbf{Data-lake migration.} Source contributions were migrated from
  a personal Google Drive to the organizational \textbf{CalCOFI Data
  Folder} shared drive, with \texttt{rclone}-based GDrive→GCS sync via a
  dedicated \texttt{calcofi-admin} service account (provisioned with
  Erin's help), establishing the long-term archive.
\end{itemize}

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{2. Visualize --- On-the-Fly Hexagons, Management Areas, and
Partner
Dashboards}\label{visualize-on-the-fly-hexagons-management-areas-and-partner-dashboards}

\begin{itemize}
\item
  \textbf{On-the-fly hexagon tile service (the cached-endpoint
  deliverable).} The integrated app previously pre-computed hexagon
  summaries for all zoom levels across the entire study area. A new
  \textbf{H3T tile API} now summarizes only the current zoom level and
  map extent on demand. It was prototyped as an R/Plumber service
  (\texttt{api-h3t}), then rewritten as a FastAPI service
  (\texttt{api-h3t-py}) with multi-database support, fronted by Varnish
  caching and edge gzip/zstd compression at \texttt{h3t.calcofi.io}. The
  integrated app reads hex data from it behind a \texttt{USE\_H3T} flag.
\item
  \textbf{Management areas of interest.} The integrated app
  (\texttt{db-viz-hex}) gained spatial layers for maritime zones, marine
  protected areas, and wind energy areas, plus a dark/light theme,
  reproducible query/data download bundles, and a direct connection to
  the \texttt{calcofi4r} Parquet database (replacing the old API
  dependency).
\item
  \textbf{Standalone and partner apps.} New/redesigned Shiny apps
  include \textbf{\texttt{ctd-viz}} (linked map/table, plotly transects,
  GEBCO bathymetry), a \textbf{\texttt{datacheck}} cross-dataset
  observation explorer with deep-linkable URLs, and a \textbf{cruises}
  explorer. Three 2026 student-capstone visualization products were also
  supported and now ship from GitHub Pages: the \textbf{UCSB Station
  Data Portal}, the \textbf{UCSB Larvae Dashboard}, and the \textbf{UCLA
  California Ocean \& Coastal Monitoring Inventory} map --- extending
  the partner coalition envisioned in the SOW.
\end{itemize}

\subsection{3. Share --- Publishing to ERDDAP \& OBIS, plus Discovery
Tools}\label{share-publishing-to-erddap-obis-plus-discovery-tools}

\begin{itemize}
\item
  \textbf{ERDDAP.} A CalCOFI-branded ERDDAP server was configured and
  deployed, serving multiple \texttt{EDDTableFromParquetFiles} datasets
  (bottle, phytoplankton, and others). A dedicated benchmark study
  compared Parquet, NetCDF (\texttt{EDDTableFromNcCFFiles}), and DuckDB
  serving backends to choose the best layout --- prompted by the wide
  CTD table OOM-ing ERDDAP's heap, which remains the one open serving
  issue (see crosswalk).
\item
  \textbf{OBIS.} The fish eggs \& larvae → OBIS workflow (Darwin Core +
  EML, joining biological observations to CTD environment by cruise) was
  refined to use the stable UUID keys and ichthyo-only scope.
\item
  \textbf{Discovery \& documentation.} Two new browser-based, serverless
  tools were built and linked throughout the docs: a \textbf{Schema
  explorer} (\texttt{schema/} --- diagram, tables, columns, datasets,
  measurements, with a cross-tab dataset filter and clickable ERD) and a
  \textbf{Query playground} (\texttt{query/} --- a Jekyll + DuckDB-WASM
  SQL sandbox). \texttt{calcofi4r} was rewired to read release
  \texttt{metadata.json}, emits \texttt{llms.txt}, and documents
  bio↔environment matching helpers; the \texttt{docs} site added Data
  Access and Matching pages.
\item
  \textbf{Webinar series --- pending.} The final Share deliverable (a
  recorded webinar series) has not yet been produced; a progress deck
  (Dec 2025 -- Jun 2026) was assembled in its place.
\end{itemize}

Over the past several months, CalCOFI's software and data systems have
advanced significantly toward a unified, reliable, and user‑friendly

\subsection{A More Capable, User-Friendly Integrated
App}\label{a-more-capable-user-friendly-integrated-app}

The \textbf{CalCOFI integrated application (\texttt{db-viz-hex})} has
evolved into a much richer and more intuitive tool for scientists and
partners:

\begin{itemize}
\item
  \textbf{Taxonomy-aware exploration}\\
  The app now understands species and their taxonomic relationships.
  Users can browse taxa hierarchies, see taxonomic ranks, and work with
  improved species metadata tied to authoritative sources (e.g., WoRMS,
  ITIS). This makes it easier to find and compare species and groups of
  species consistently.
\item
  \textbf{Better visual experience and theming}\\
  A new \textbf{dark/light theme toggle} has been implemented and
  refined so that maps, time series, and other plots remain readable and
  visually consistent. Navigation has been reorganized, with a clearer
  About page, a guided ``tour'' of the app, and more intuitive icons and
  labels, making the app easier to learn and use.
\item
  \textbf{Stronger spatial and temporal tools}\\
  Spatial maps now rely on efficient hexagon grids calculated in the
  database, improving performance and scalability. Default settings for
  time and depth matching have been tuned to yield better joins between
  environmental and biological data out of the box.
\end{itemize}

Overall, the app is moving from a prototype to a \textbf{polished,
guided interface} that better supports exploratory analysis and
communication.

\begin{center}\rule{0.5\linewidth}{0.5pt}\end{center}

\subsection{A Stable, Well-Documented Database
Foundation}\label{a-stable-well-documented-database-foundation}

The \textbf{CalCOFI database package (\texttt{calcofi4db})} has been
formalized and versioned, providing a solid foundation for all
downstream tools:

\begin{itemize}
\tightlist
\item
  \textbf{Two stable releases} (versions 1.0 and 1.1) have established a
  reliable baseline for the database, including bottle-level data.
\item
  The project now follows a \textbf{clear strategy for separate
  development and production databases}, reducing risk when making
  changes and improving reproducibility.
\item
  Data ingestion from NOAA and other sources has been \textbf{hardened},
  with several rounds of fixes to handle edge cases and ensure that raw
  files are consistently and correctly translated into the database.
\end{itemize}

In addition, the package's \textbf{online documentation site} has been
refreshed so that developers and analysts have up-to-date guidance on
how data flow into and through the database.

\subsection{Unified R Tools and Documentation Around
DuckDB}\label{unified-r-tools-and-documentation-around-duckdb}

Across the toolchain, CalCOFI has standardized on \textbf{DuckDB} as the
core data engine:

\begin{itemize}
\tightlist
\item
  The \textbf{R package (\texttt{calcofi4r})} now encapsulates key logic
  originally developed inside the integrated app, so the same
  high-quality data access and processing is available in scripts,
  reports, and analyses---not just in the web interface.
\item
  Both the app and R package can connect to \textbf{local or remote
  DuckDB databases}, improving performance and enabling offline or
  near‑offline workflows.
\item
  Documentation in the \textbf{\texttt{docs} repository} has been
  updated to describe the full data creation process (from raw data to
  ready‑to‑use databases) and to explain the new development/production
  database strategy. Status documents and helper scripts provide clearer
  visibility into project progress.
\end{itemize}

This brings CalCOFI closer to a \textbf{coherent, documented platform}
where analysts can move seamlessly between app-based exploration and
scripted analysis.

\subsection{Standards-Compliant Publication of Biological
Data}\label{standards-compliant-publication-of-biological-data}

The \textbf{\texttt{workflows}} repository has seen major progress in
turning CalCOFI's biological datasets into \textbf{publication-ready
products}:

\begin{itemize}
\tightlist
\item
  New workflows now \textbf{publish larval data to OBIS}, the global
  biodiversity information system, with repeatable recipes that combine
  biological observations with CTD (oceanographic) data.
\item
  The underlying data model for \textbf{events and occurrences} has been
  strengthened to align with international standards (e.g., Darwin
  Core), including:

  \begin{itemize}
  \tightlist
  \item
    Clear hierarchies of sampling events,
  \item
    Better handling of life‑stage and size information (e.g., egg and
    larval stages),
  \item
    Automated generation of metadata files required for data archives.
  \end{itemize}
\item
  Additional integrity checks and foreign key relationships help ensure
  that data are correct and consistent before publication.
\end{itemize}

These advances substantially improve CalCOFI's ability to \textbf{share
high-quality, well-structured biodiversity data} with the broader
scientific community.
